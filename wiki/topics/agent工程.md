# Agent 工程

## 摘要

「Agent 工程」关注**单个 Agent 会话的技术实现**：系统提示与上下文如何组织、工具调用如何往返、上下文如何被压缩、记忆如何跨会话延续。它以 [[claude-code|Claude Code]] 为当前主要样本，核心问题是：**在上下文窗口已做到 1M 的时代，为什么仍然需要上下文管理？** 答案在于两条底层机制——[[kv-cache|KV Cache]] 与 [[注意力机制]]。

### 核心结论

- **上下文管理只做两件事**：顺应 KV Cache 前缀缓存以降成本；裁剪组织上下文以解决注意力问题。详见 [[上下文管理]]。
- **单向追加是默认纪律**：只有保证老内容不动、新内容垫后，才能最大化命中前缀缓存。
- **传统四方案都有代价**：摆烂报错、滑动窗口、摘要压缩、外挂 RAG，共同问题是"要么丢细节，要么牺牲速度与成本"。详见 [[上下文压缩]]。
- **上下文管理 ≠ 记忆**：它只是在窗口内"拆东墙补西墙"，跨会话的长期记忆才是下一步。详见 [[长期记忆]]。

### 六大 Token 杀手（速查）

膨胀的 `CLAUDE.md`、贪多挂载的 MCP、滥用的 Skill/斜杠命令、失控的 Tool Result、未压缩前的历史包袱、暗中狂飙的 Thinking Tokens。详见 [[上下文管理]]。

### 主题边界

- 本主题关注**技术实现层**；[[ai原生软件开发]] 关注**组织与流程层**。
- 两者通过 [[claude-code]]、[[建议性控制与确定性控制]] 交叉：流程层的 hook/skill 分层，正是建立在会话层"建议性加载 / 确定性拦截"的能力之上。
- Agent 的**商业应用层**（获客/线索生成自动化）见 [[agent自动化获客]]，其可移植工作流机制见 [[skill文件]]——应用层与实现层的分工模式（agent 执行、人保留判断）与本主题"建议性/确定性控制"同构。
- 本主题目前仅有单一来源（系列第一篇），后续"长期记忆"等篇章入库时应在此扩写，并保留不同说法。

### 两条工程路线（分歧并存，第 6 批后新增）

本库目前记录了一组**明确的路线对立**——同为 agent 工程，但解法相反：

| 维度 | 事后治理派 | 事前极简派 |
| --- | --- | --- |
| **代表人物 / 来源** | @coder-left（[[agent工程解析-上下文管理]]） | [[armin-ronacher|Armin Ronacher]]（[[armin-ronacher-九条反直觉判断]]） |
| **代表产品** | [[claude-code|Claude Code]]（全功能 harness） | [[pi-agent|Pi]]（极简 harness） |
| **主张** | 上下文必然膨胀，故需研究**压缩、裁剪、外挂记忆**等治理机制 | 框架本体不预置功能，从源头避免膨胀；**只给 bash 等基础工具** |
| **上下文开销** | 视为必须治理的对象 | 视为"恒定税"，主张**按需付费**（渐进披露） |
| **共识** | 上下文是稀缺资源 | 上下文是稀缺资源 |
| **分歧** | 事后治理 | 事前极简 |

> 详细展开见 [[harness-极简主义]]；两条路线**各有代价**（极简派上手成本高、无内置沙箱；全功能派有恒定 token 税但开箱即用），本库**并列保留，不取单一结论**。

### 新增维度：人的位置

- [[可内省性]]（Ronacher）：人必须能亲眼看到 agent 做了什么，因为"**机器不可问责**"——这与本库 [[审批门]]、[[建议性控制与确定性控制]] 的关注点互补（前者解决"能不能拦住"，后者解决"人是否理解"）。

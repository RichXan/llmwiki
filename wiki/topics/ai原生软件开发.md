# AI 原生软件开发

## 摘要

「AI 原生软件开发」讨论的是：当 Agent 承担了大部分代码产出后，软件开发生命周期（SDLC）**如何在不放弃原有控制目标（问责、审计、职责分离、变更管理）的前提下，换一套执行方式**。当前本库以 Anthropic 手册《The AI-Native SDLC playbook》及其中文解读为主要来源，它的核心贡献是一套可借用的词汇：**[[产物链]]、[[审批门]]、hook、[[eval-套件]]、闭环**。

## 核心内容

### 问题：瓶颈从"写代码"转移到"流程"

构建阶段从几周压缩到几小时后，计划、评审、测试、部署仍按人的速度运行，导致瓶颈转移、控制手段与现实脱节、治理成本上升。结论是：实现阶段的变革程度，整个 SDLC 都要经历同等变革。详见 [[ai原生sdlc]]。

### 三个支撑机制

1. **线性流程 → 循环流程**（维护发现的意图回流到计划）。
2. **每个阶段以提交一份产物结束**（早期是 Markdown，后期是代码与记录），提交链本身即审计轨迹。详见 [[产物链]]。
3. **人的注意力集中在"门"上**（接受产物即触发下一阶段，人只审 agent 标记的问题）。详见 [[审批门]]。

### 六个阶段与产物

| 阶段 | 产物 | 进入下一阶段的触发 | 关键动作 |
| --- | --- | --- | --- |
| Plan | [[意图文件\|intent.md]] | 产品负责人接受 | 发起人用自己的话写意图；非工程师经 claude.ai / Cowork 提交 |
| Design | `spec.md` | 产品负责人批准 | 需求与设计合并为一次会话，负责人**只审不写** |
| Build | `plan.md`、diff、测试 | 工程师接受计划 | plan mode 起步；计划未通过不能改文件；CLAUDE.md / Skill / Hook / 并行会话 |
| Test | 测试输出、CI check run | 检查通过 | 反馈回路；修 bug 先写失败测试；[[eval-套件]] |
| Deploy | 带评审记录的 PR | code owner 批准合并 | agent 完成生产门之前的一切，但不跨过生产门 |
| Maintain | 事故记录 → 新的 intent.md | 控制带被突破 | 确定性脚本监控 + 分级响应 + 闭环 |

### 两条贯穿性设计原则

- **建议性控制与确定性控制分两层**：Skill/CLAUDE.md/prompt 让正确行为成为大概率事件；hook/沙箱/分支保护/托管设置让"必须成立"的策略真正成立。详见 [[建议性控制与确定性控制]]。
- **Agent 不能批准自己的工作，也不能削弱对自己工作的检查**；引导 agent 的配置与代码同等对待（进 git、走 review、跑 eval）。

### 适用范围与局限（解读作者观点）

- 适合已在用 agentic 编码工具、感到流程跟不上代码的**中大型组织**，尤其受监管行业；小团队可只取几个 play（plan mode、CLAUDE.md、反馈回路、AI 评审）。
- 这是一篇**产品文章**，落地细节绑定 Claude 生态（Claude Code / Design / Security / Tag / Cowork），原则与产品需分开看；前置条件不轻（依赖单命令测试套件、可靠构建、成熟 CI/CD）；人的评审是隐含上限。

### 与其他主题的边界

- 与 [[agent工程]] 相关但不同：本主题关注**组织/流程层**，agent工程关注**单个会话与上下文的技术实现**；两者通过 [[claude-code]]、[[建议性控制与确定性控制]] 交叉。
- 与 [[自生长个人知识库]] 同属"AI 驱动的工作方式"，但一个面向工程组织，一个面向个人知识管理。

# 来源摘要：AI 自动修改 UI 总是翻车

## 摘要

本文作者（X：[@Lonely__MH](https://x.com/Lonely__MH)）记录用 AI **复刻页面**（截图转代码）时踩的坑，并给出解法：把**渲染 → 截图 → 逐像素 Diff → 先诊断再改代码 → 保留历史最佳**串成一个自愈工作流，让模型自己检查、自己改。作者的核心发现是：**Diff 只是工具，不是裁判**——反馈流程本身出错时，模型只会非常认真地往错误方向修。文中归纳了三个坑与三条规则，详见 [[视觉自愈循环]]。

## 核心内容

### 1. 要解决的问题

把一张截图丢给 AI 让它照做页面，第一版总"差不多但差一点"：卡片宽一截、字号小点、阴影不对——只能反复口述让它调，很费时间。作者的思路是把"渲染、截图、对比、修改"串成工作流，让模型自检自改。

### 2. 工作流

```text
目标截图 ──▶ 模型写 HTML ──▶ 浏览器 1:1 渲染截图 ──▶ 逐像素比对生成 Diff
                                                         │
保留历史最佳 ◀── 重新渲染 ◀── 模型先写诊断再改代码 ◀── 原图 + 渲染图 + Diff
```

- **Diff 不替模型修页面**，只是把"感觉不太像"变成能看到具体偏差的图，再交回模型判断下一步改什么。
- **改之前先答三问**：① 最大的问题在哪里；② 可能是哪个元素、哪个 CSS 属性造成的；③ 准备怎么改。说完再动代码。

### 3. 实验结果（两张卡片的两种走势）

- **亮黄卡片**：第二轮更接近原图，**第三轮又回落**，最终保留第二轮的历史最佳。
- **深色 SaaS 定价卡片**：三轮都在小幅往前走（继续抠尺寸、圆角、按钮、渐变）。
- 结论：**同一套流程跑起来，不一定每一轮都比上一轮好**；明显问题通常前一两轮修掉，后面全是细节，"改一处很容易又碰坏另一处"。所以**保存历史最佳，而不是默认把最后一轮当答案**。
- 作者强调：两次录屏说明不了统计规律。

### 4. 它到底能做什么

- 第一版就是常见的 **Screenshot-to-Code**。
- 真正有意思的是：模型看完渲染结果后，能**把问题落到具体元素和 CSS 上**，而不是只说"再像一点"；即使不开自动改，这段诊断也能当检查清单用。
- 很多视觉问题**不会触发报错**，模型看到浏览器真正渲染的页面就有机会自己往下改。

### 5. 三个坑（真正花时间的地方）

1. **尺寸**：目标图被缩放过，浏览器又用另一个尺寸截图，两张图从一开始就没对齐——**整体偏几像素就能炸出一大片误差**，连"标准答案"放进去 Diff 都一大片。
2. **动画**：模型给功能列表加了淡入，截图时动画没播完、内容还是透明的；去掉动画后肉眼正常了，自动比对结果**反而更差**——因为内容透明时露出背景，像素算法反觉得"更像"。
3. **版本**：这一轮已经改坏，还继续在这版代码上打补丁，错误会一层层叠加，"跟在歪掉的地基上继续盖楼"。

> 核心论断：**Diff 只是工具，不是裁判。如果反馈本身是错的，模型不会替我发现这件事，它只会拿着这份反馈非常认真地修错方向。**

### 6. 最终三条规则

1. 原图和浏览器截图使用**同一尺寸**，不再二次缩放；
2. 固定**视口、字体、动画状态和截图时机**；
3. 每轮从**历史最佳版本**继续，不在变差的代码上叠补丁。

作者补充：不会默认"轮数越多越好"——先把明显问题修掉，后面不再变好就停。

### 7. 性能与模型信息

- 单次整页 HTML 生成约 **7 秒**（作者当时那套接口与设置下的调用记录，未做横向对比，也不建议用激活参数直接推导速度与成本）。
- 公开资料称 [[ling-3-flash-vl|Ling-3.0-flash-VL]] 总参数 **124B**、每次推理激活 **5.5B**，加入视觉理解与 Visual Agent 能力。

# 来源摘要：Agent 工程解析（一）：上下文管理

## 摘要

本文作者（X：@coder_left）从底层原理出发，以 [[claude-code|Claude Code]] 为例，系统拆解大模型的上下文管理：先区分"长期记忆（权重参数）"与"短期记忆（上下文窗口）"，再从 **KV Cache** 与**注意力机制**两条底层机制解释"为什么 1M 上下文时代仍需要上下文管理"，随后剖析 Claude Code 的上下文组成（三层）、`CLAUDE.md` 的五类形态、会话中上下文的变化、六大"Token 杀手"、上下文超限的传统四方案，以及 Claude Code 的五级防御机制。文末强调：上下文管理不是真正的记忆，跨会话的**长期记忆**才是下一步。

## 核心内容

### 1. 大模型的两种记忆

- **长期记忆（权重参数）**：预训练/微调阶段固化，会话中稳定生效，但无法实时更新。
- **短期记忆（上下文窗口）**：会话级动态驻留，能否记得某事取决于内容是否还在窗口内；新会话、清空、超出窗口都会"失忆"。详见 [[长期记忆]]。

### 2. 为什么需要上下文管理

两条底层机制决定了工程实现：

- **KV Cache 机制**：推理单向逐字进行，缓存已算好的中间状态以避免重复计算。**命中缓存的价格通常是非命中价的 1/10～1/50**，但物理规则是**前缀必须绝对一致**，中间改一个字，其后缓存全部失效。详见 [[kv-cache]]。
- **注意力机制**：注意力像一盏"聚光灯"，内容越多越杂越分散；过长、过杂的上下文（大量工具报错、未截断日志、废弃标签）会让关键约束被淹没，产生幻觉。详见 [[注意力机制]]。

由此，上下文管理本质上只做两件事：**顺应 KV Cache 前缀缓存降成本** + **裁剪组织上下文解决注意力问题**。详见 [[上下文管理]]。

### 3. 从 Claude Code 看上下文组成（新建会话约 25K tokens）

组件占比：工具定义（~10K，27 个工具的 JSON Schema）、Claude Code 主指令（~5K）、auto memory（~3K）、环境信息（~0.5K）、Skills 列表（~1.5K）、全局 CLAUDE.md（~100）、项目 CLAUDE.md（~4K）、当前日期（~50）、本地命令记录（~300）。逻辑分三层：

- **静态指令层（绝对稳定）**：官方硬编码的身份、安全底线、代码风格与执行规范——越稳定越焊在最前。
- **弱动态层（低频变动）**：项目路径、系统环境、Git 状态、CLAUDE.md 等，单个会话内几乎不动。
- **强动态层（高频变动）**：Messages 列表里不断追加的交互消息。

排序即"梯形结构"，服务两个目的：前缀稳定以吃满缓存折扣；用克制剪枝保护注意力（Skill 渐进式加载、工具延迟加载、Memory 超 200 行或 25KB 硬截断）。

### 4. CLAUDE.md 的五类形态（从"谁管谁"理解）

| 层级 | 路径 | 作用 |
| --- | --- | --- |
| 托管策略级（公司管机器） | macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`；Linux `/etc/claude-code/CLAUDE.md` | 企业 IT 强制合规，跨全机生效，开发者无权改 |
| 用户全局级（自己管所有项目） | `~/.claude/CLAUDE.md` | 跨项目个人偏好，仅本机、不入库 |
| 项目共享级（团队管当前项目） | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 团队公共契约，纳入 Git |
| 项目本地私有级 | `./CLAUDE.local.md` | 个人本地覆写，写入 `.gitignore` |
| 子目录级（Monorepo） | `<子目录>/CLAUDE.md` | 只在特定路径生效的技术约束 |

装配流程朴素：CLI 以当前工作目录为基准，按**系统托管 → 用户家目录 → 项目根 → 工作子目录**拼接全部规则文件，**不做物理覆盖或去重**。所谓"局部覆盖全局"全靠 Transformer 的注意力倾向（更靠后、更具体的句子权重更高），并非确定性拦截。顺序自顶向下编排的目的仍是**配合 KV Cache**：把低频改动的前置项焊死，把易变项垫后，改它们只破坏尾部缓存。

### 5. 会话进行中，上下文如何变化（Agent Loop）

- 消息组织绝大多数是**单向追加到末尾**（配合前缀缓存）。Anthropic API 用 Messages 列表，每条含 `role`（user/assistant）与 `content`。
- **场景一**：用户输入 → 追加 `role: user` 消息。**场景二**：直接作答 → 响应 `stop_reason: end_turn`，追加 `role: assistant`。**场景三**：发起工具调用 → `stop_reason: tool_use`，`content` 含 `tool_use` 块（`id`/`name`/`input`）。**场景四**：回传结果 → **Anthropic 规定工具结果必须封装为 `role: user` 消息**，`content` 放 `tool_result` 块（`tool_use_id` 必须与 `tool_use.id` 一致）。

详见 [[agent-loop]]。

### 6. 六大"Token 杀手"

1. **膨胀的 CLAUDE.md**（每轮全量带上，根目录宜压 200 行内）；
2. **贪多挂载的 MCP**（一个 Server 十几个工具，挂三四个就是两三万 Token；靠工具延迟加载缓解）；
3. **滥用的 Skills 与斜杠命令**（渐进式加载≠无上限，易引发工具冲突与"选择困难"）；
4. **失控的 Tool Result**（最凶；Claude Code 做"中间截断"兜底，更稳妥的是主动加 `| head -n 50`、`grep`、SQL `LIMIT`）；
5. **未触发压缩前的历史包袱**（垃圾上下文在每轮反复计费，压缩本身也是一次昂贵调用）；
6. **暗中狂飙的 Thinking Tokens**（复杂任务值得开思维链，简单任务应降级）。

### 7. 上下文超限：传统四方案的局限

**摆烂报错流**（硬拦截、体验断裂）→ **滑动窗口流**（擦掉最早 N 轮，常把最初的全局需求/架构铁律擦掉，变"金鱼脑"）→ **摘要压缩流**（摘要质量不可控，关键行号/字段易被"优化"掉）→ **外挂 RAG 流**（延迟与成本双重暴击，召回精度看运气，易召回过期毒药）。共同问题：要么丢细节，要么牺牲速度与成本。

### 8. Claude Code 的五级防御机制

| 级别 | 名称 | 做法 |
| --- | --- | --- |
| 1 | 大工具输出落盘 | 超阈值（如 20KB）→ 完整落盘 `~/.claude/projects/.../tool-results/`、只留约 2KB 预览、注入本地文件路径指针 |
| 2 | Snip compact | 每轮巡检，Token 增量达 **10K** 触发，按 Message ID 抹掉低价值消息（动作最轻、频率最高；官方未公开完整实现） |
| 3 | Micro compact | **消息不动，只清理可重复/幂等的 tool_result**（读文件、grep、glob、只读 shell、编辑写入等白名单）；含 TimeBasedMicrocompact（闲置超期缓存已失效时随意清）与 CachedMicrocompact（用 `cache_reference` + `cache_edits` 在不破坏前缀的前提下原地扣减）两种模式 |
| 4 | Context collapse | 后台预计算消息区间摘要草稿（staged），撞阈值时静默替换为 `[U1, A1, S1, U5]` |
| 5 | Full compact | 全量压缩：预留 20K 输出（p99.99 为 17,387）；三道水位线（有效窗口 = 总量 −20K；触发 = 有效 −13K，约 93%；告警 = 再 −20K，约 80%）；单独子 Agent 总结，提示词头尾双重禁止调用工具（因 Sonnet 4.6 自适应思考易误调工具、`maxTurns:1` 会导致失败，失败率 2.79% vs 4.5 的 0.01%）；输出 `<analysis>`（草稿、丢弃）+ `<summary>`（**9 维结构化**：意图/技术概念/文件与代码/错误与修复/问题求解/全部用户消息/待办/当前工作/下一步建议）；收尾清状态、重挂附件、跑 Hook、组装含边界标记的新结构 |

详见 [[上下文压缩]]。

### 9. 人机协同的上下文管理技巧

结构编排（静态前置、易变垫后）；能延迟加载就不一次性全倒；严格克制 CLAUDE.md 体积（100–200 行，详细架构拆独立文档）；精简挂载的 MCP 与 Skill；养成随手限制工具输出的习惯。

### 10. 上下文管理 ≠ 记忆

上下文治理只是"当前窗口里拆东墙补西墙"，信息在不可逆地流失；关掉终端或 `/clear` 后默契与关键决策全部消失。真正的顺手靠**跨会话的长期记忆**（作者预告将单独一期讲解）。详见 [[长期记忆]]。

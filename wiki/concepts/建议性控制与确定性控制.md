# 概念：建议性控制与确定性控制

## 摘要

**建议性控制与确定性控制** 是 AI 原生 SDLC 中最具迁移价值的一条原则：把对 Agent 的约束分成两层——**建议层**让正确行为成为大概率事件，**确定层**让"必须成立"的策略真正成立。凡是"必须成立"的策略，建议层背后都要有确定层兜底。来源见 [[从intent到闭环-ai原生sdlc]]。

## 核心内容

### 两层划分

| 层 | 载体 | 性质 |
| --- | --- | --- |
| **建议层** | Skill、`CLAUDE.md`、prompt | 建议性控制：让 Claude 大概率应用策略，但没有东西强迫会话遵守 |
| **确定层** | hook、沙箱、分支保护、托管设置 | 确定性控制：拦截操作、强制执行，会话无法绕过 |

### 来源中的关键论断

> **Skill 让违规变少，hook 让违规几乎不可能发生。**

- **Skill 是一种控制，但是建议性的控制。** 必须始终成立的策略，需要 skill 背后有确定性的东西——比如拦截操作的 hook，或在 PR 阶段重新检查的评审。
- **构建期 hook** 只作用于改动文件、必须快；重型检查放到 commit 或 PR；**需要人审批的 hook 不放在构建阶段**（会把人也变成并行会话的关键路径）。
- **`REVIEW.md` 评审发现** 属于建议层，不批准也不阻塞 PR，真正的强制力来自分支保护。

### 其他"确定层"手段

- 沙箱与托管设置（`permissions.deny/allow`、`disableBypassPermissionsMode`、`sandbox`、`credentials`、`requiredMinimumVersion` 等，详见 [[审批门]]）。
- 分支保护（要求 code owner 批准）。
- 修 bug 时用 hook 阻止对测试文件的编辑——**修代码的 agent 不能削弱对自己工作的检查**。

### 迁移价值

这套"建议 / 确定"分层不限于 Claude 生态：任何 Agent 系统都可以照此检查——"必须成立"的规则，是否只有一句自然语言在撑着？如果是，就不算控制。

参见 [[上下文管理]] 中的相关印证：`CLAUDE.md` 的"局部覆盖全局"也没有确定性拦截机制，全靠注意力倾向，属于典型的**建议层**。

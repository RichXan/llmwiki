# 概念：上下文管理

## 摘要

**上下文管理** 指 Agent 在会话过程中，对送入模型的上下文进行组织、裁剪与压缩的一整套工程做法。来源结论：即使上下文窗口已做到 1M，上下文管理仍然必要——因为它本质上只做两件事：**顺应 [[kv-cache|KV Cache]] 前缀缓存以降低推理成本**、**通过裁剪与组织解决 [[注意力机制|注意力]] 问题**。来源见 [[agent工程解析-上下文管理]]。

## 核心内容

### 为什么需要

- 早期窗口小，"聊着聊着就提示上下文已满"。
- 窗口变大后衍生新问题：**成本控制、注意力稀释、幻觉**。
- 从工程视角归纳为两类机制：KV Cache（成本）与注意力（质量）。

### 上下文的梯形结构（三层）

| 层 | 变动频率 | 内容 | 排序理由 |
| --- | --- | --- | --- |
| 静态指令层 | 绝对稳定 | 身份声明、安全底线、代码风格、执行规范（官方硬编码） | 越稳定越焊在最前，吃满缓存折扣 |
| 弱动态层 | 低频变动 | 项目路径、系统环境、Git 状态、`CLAUDE.md` 等 | 单会话内几乎不动 |
| 强动态层 | 高频变动 | Messages 列表里不断追加的交互消息 | 垫在最后，改动只破坏尾部缓存 |

### 初始化时的克制剪枝

- **Skill 渐进式加载**：只先加载名字与一两句元数据，需要时才动态抓取。
- **工具延迟加载**：冷门工具只保留名字 + 一个 `tool_search` 查询工具。
- **Memory 物理硬截断**：读取的记忆超过 **200 行**或大于 **25KB** 直接硬截断。

### 六大 Token 杀手

1. 膨胀的 `CLAUDE.md`（每轮全量带上；宜压 200 行内，定期除草）；
2. 贪多挂载的 MCP（工具 Schema 体积大，靠延迟加载缓解）；
3. 滥用的 Skills 与斜杠命令（易引发工具冲突与"选择困难"；命名与描述要极简）；
4. 失控的 Tool Result（最凶；主动加 `| head -n 50`、`grep`、SQL `LIMIT` 防御）；
5. 未触发压缩前的历史包袱（垃圾上下文反复计费，压缩本身也昂贵）；
6. 暗中狂飙的 Thinking Tokens（复杂任务开思维链，简单任务降级）。

### 人机协同技巧

静态前置、易变垫后；能延迟加载就不全量倒入；严格克制 `CLAUDE.md` 体积（100–200 行，架构拆独立文档）；精简挂载的 MCP 与 Skill；养成随手限制工具输出的习惯。

### 一个反直觉的推论

`CLAUDE.md` 的"局部覆盖全局"**没有确定性拦截机制**——底层只做纯文本拼接、不做键值覆盖或去重，覆盖效果全靠模型对"更靠后、更具体"句子的注意力倾向。因此它属于典型的**建议性控制**（见 [[建议性控制与确定性控制]]），写错/自相矛盾会导致模型"随机漂移"。

### 与"记忆"的区别

上下文管理管的是"这几小时的短期草稿"，关掉终端或 `/clear` 后全部消失；它不是真正的记忆。详见 [[长期记忆]]、[[上下文窗口]]。

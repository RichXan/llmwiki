# 概念：审批门（Gate）

## 摘要

**审批门** 是 AI 原生 SDLC 中"人的注意力集中处"：一个产物被接受，就触发进入下一阶段；人只在门口审阅 agent 标记出来的问题。其目标状态是"每个被接受的产物自动触发下一道门"，从而把人的时间从"逐条盯着 agent 改"转移到"审阅产物与风险"。来源见 [[从intent到闭环-ai原生sdlc]]。

## 核心内容

### 门的两类实现

- **构建期护栏（hook）**：只有"允许/阻止"两种结果，用途包括拦截对受保护路径的编辑、改完文件自动跑 formatter/linter、把凭据挡在 diff 之外。构建期 hook 要快、只作用于改动文件，**不放需要人审批的 hook**——否则会把人放回所有并行会话的关键路径上。
- **审批门（会"询问"的 hook）**：hook 也可以"询问"，暂停操作直到指定的人批准，这正是发布门所需的形态。做法是把必须保留的人工审批（变更签字、发布授权、受保护路径编辑）逐条写成 hook；团队级 hook 放 `.claude/settings.json`，**不可协商的 hook 放"托管设置"**，工程师关不掉。阻止时要说明原因与申请审批的途径。

### 受监管企业的托管设置（控制要点）

| 配置项 | 作用 |
| --- | --- |
| `permissions.deny` | 把密钥挡在上下文之外，封锁工具层的网络出口 |
| `permissions.allow` | 预批准安全的内循环，避免 deny 太多造成 prompt 疲劳 |
| `disableBypassPermissionsMode` + `allowManagedPermissionRulesOnly` | 任何工程师、项目文件、命令行参数都无法放宽规则 |
| `sandbox` | 补权限漏洞：工具层禁用 WebFetch 挡不住 shell 访问网络，需 OS 级域名白名单 |
| `failIfUnavailable` | 沙箱起不来时直接拒绝启动 |
| `credentials` | 补另一个漏洞：文件工具的 deny 管不住沙箱里的 shell 读取 `~/.ssh` |
| `allowManagedHooksOnly`、`disableSideloadFlags`、`strictKnownMarketplaces`、`allowManagedMcpServersOnly` | 所有 skill/agent/hook/MCP server 只能来自组织批准的插件市场 |
| `requiredMinimumVersion` | 拒绝在评估过的版本以下启动 |

### 职责分离

- 分支保护仍要求 code owner 批准；`REVIEW.md` 的评审发现**不批准也不阻塞** PR。
- 关键点：**写代码的 agent 没有途径批准它自己的 PR**——职责分离因此得以保留。

### 部署与闭环中的门

- 部署原则：**agent 可以完成生产门之前的一切工作，但不能跨过这道门**；生产环境由 agent 准备发布、发布经理授权、hook 强制执行。
- 维护闭环中按 `bands.yaml` 分级：1σ 只记日志、2σ 只读诊断、3σ 可行动但只能向评审门开 PR 或触发预批准 runbook。
- 回滚应是流水线里**演练最多的路径**，因为闭环会在指标越界时调用它。

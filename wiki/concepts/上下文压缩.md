# 概念：上下文压缩

## 摘要

**上下文压缩** 是 [[上下文管理]] 中"容量治理"的部分，即上下文接近窗口上限时如何腾出空间。来源先梳理工业界**传统四方案**的局限，再给出 [[claude-code|Claude Code]] 的**五级防御机制**：由轻到重，针对不同膨胀程度逐步拆招。来源见 [[agent工程解析-上下文管理]]。

## 核心内容

### 一、传统四方案及其局限

| 方案 | 做法 | 局限 |
| --- | --- | --- |
| 摆烂报错流 | 超限直接抛异常，要求新开会话 | 体验断裂，连续协作不可能 |
| 滑动窗口流 | 剔除队列最老的消息，只留最近 N 条 | 变"金鱼脑"，最老的消息常是最初的全局需求/架构铁律 |
| 摘要压缩流 | 把前半段历史总结成几百字替换 | 摘要质量不可控，关键行号/字段/环境变量易被"优化"掉 |
| 外挂 RAG 流 | 历史切片向量化入库，按需语义检索 | 延迟与成本双重暴击；召回精度看运气，易召回过期"毒药" |

共同结论：传统方案**要么在丢弃细节，要么在牺牲速度与成本**。

### 二、Claude Code 的五级防御

| 级别 | 名称 | 做法要点 |
| --- | --- | --- |
| 1 | 大工具输出落盘 | 超物理阈值（如 20KB）时：完整落盘 `~/.claude/projects/.../tool-results/`、只留约 2KB 预览、注入本地文件路径指针（`<persisted-output>`） |
| 2 | Snip compact | 每轮巡检，Token 增量达 **10K** 触发一次评估；按 Message ID 抹除低价值消息。动作最轻、频率最高。**官方未公开完整实现，属推测轮廓** |
| 3 | Micro compact | **消息不动，只清理可重复/幂等的 `tool_result`**（读文件、grep、glob、只读 shell、编辑写入等白名单）。两种模式：<br>· **TimeBasedMicrocompact**：闲置超 60 分钟（缓存已过期）时可随意清；<br>· **CachedMicrocompact**：给待删工具结果打 `cache_reference`，在最后一条 user 消息里塞 `cache_edits`，**在不破坏已有前缀缓存的前提下原地扣减**；上一轮的 edits 作为 pinnedEdits 固定保留 |
| 4 | Context collapse | 后台预计算一段连续消息的摘要草稿（staged，含 startUuid/endUuid/summary/risk/stagedAt），**不立刻改上下文**；撞阈值时直接替换为 `[U1, A1, S1, U5]`，前台基本无卡顿 |
| 5 | Full compact | 全量压缩（见下） |

### 三、Full compact（全量压缩）细节

- **阈值设计**：预留 20K 输出（依据：p99.99 的总结输出为 17,387 tokens）。三道水位线：有效上下文窗口 = 总量 − 20K；压缩触发阈值 = 有效窗口 − 13K（约 93%）；告警阈值 = 再 − 20K（约 80%）。
- **子 Agent 总结**：提示词头部与尾部各出现一次"禁止调用工具"的硬警告。原因：压缩子 Agent 继承父级完整工具集以保证缓存命中，而在 Sonnet 4.6+ 自适应思考模型上易误调工具，`maxTurns:1` 下被拒会导致整个压缩失败（失败率 2.79% vs 4.5 的 0.01%）。
- **输出格式**：`<analysis>`（推理草稿，最终丢弃）+ `<summary>`（**9 维结构化**）：① 原始意图 ② 关键技术概念 ③ 文件与代码片段 ④ 错误与修复 ⑤ 问题求解 ⑥ 全部用户消息 ⑦ 待办 ⑧ 当前工作 ⑨ 下一步建议（附原文引用）。
- **收尾工作**：清空旧状态（如 `readFileState.clear()`）→ 重挂上下文附件（最近文件、计划文件、激活的 Skill）→ 跑 SessionStart Hook → 组装含边界标记（时间戳、压缩前 Token 数）、摘要主体、环境附件的 `CompactionResult`。

### 四、设计取向

五级机制的共同思路：**先用"保留指针/幂等清理"这类低成本手段，把"丢细节的总结"留到最后**——尽可能减少不可逆的信息损失，同时尽量不破坏缓存前缀。

### 五、不同来源的说法差异（分歧并存）

网络检索发现，关于 Claude Code 的压缩机制，各来源在**层数、命名、顺序、触发阈值**上并不一致。按本库"分歧并存"原则，同时保留各说法与出处，不互相覆盖：

| 来源 | 口径 | 顺序 / 层级 | 关键差异 |
| --- | --- | --- | --- |
| [[agent工程解析-上下文管理]]（@coder_left，2026-09-12） | 五级防御 | 大工具输出落盘 → Snip compact → Micro compact → Context collapse → Full compact | 阈值称 93% / 80%；Snip 以 **10K** Token 增量触发 |
| AI 世界（微信公众号转述，2026） | 四级 | Microcompact → Snip Compact → Context Collapse → AutoCompact | 称 Context Collapse 与 AutoCompact **互斥**；Microcompact 为"本地、无 API 调用"的第一道防线 |
| CSDN 深度拆解（2026） | 五层 | SnipCompact → MicroCompact → Context Collapse → AutoCompaction →（第五层未列全） | 称 AutoCompact 触发阈值为**窗口 78%**；称 MicroCompact 闲置 60 分钟触发、无损、写盘 + 占位标记 |
| DEV Community 指南（2026） | 六策略 | 含 Micro-compact、Snip、Context Collapse、reactive compact 等 | 把 **reactive compact** 列为独立项；称 1M 窗口（Opus 4.6 / Sonnet 4.6）自 2026-03 GA |
| DeepWiki（对第三方 claude-code 仓库的逆向，2026） | 多类型 | Micro-compaction、Session Memory compaction、Traditional compact、Reactive compact（feature-flagged）、Snip Compaction | 命名对应源码文件名（`microCompact.ts`、`snipCompact.ts`、`sessionMemoryCompact.ts`、`reactiveCompact.ts`） |

**归纳**：可以确认的是——Claude Code 存在一条**由轻到重**的压缩流水线，包含微压缩、片段裁剪（snip）、上下文折叠、全量摘要等环节；但**具体层级归属、触发阈值、自动/手动边界在不同来源间存在明显分歧**，且多为第三方逆向或转述。

> 使用建议：把"由轻到重的多级压缩"当作稳定结论，把"哪几级、叫什么名字、阈值多少"当作**随版本变化的实现细节**，不必在单一口径上较真。

## 来源与待核实问题

- **来源**：[[agent工程解析-上下文管理]]

### 已核实（网络检索，2026-09-12）

- 多个独立来源（微信公众号转述、CSDN、DEV Community、DeepWiki）**共同确认**存在由轻到重的多级压缩流水线，且包含 Micro compact、Snip、Context Collapse、全量摘要等环节。
- **1M 上下文窗口**：多个来源称 Opus 4.6 / Sonnet 4.6 支持 1M 窗口，自 2026-03 起 GA（与 [[上下文窗口]]、[[openai]] 的讨论一致）。

### 分歧（已在正文第五节并列保留）

- 层数（4 / 5 / 6）、命名（Full compact vs AutoCompact vs Reactive compact vs Traditional compact）、顺序与阈值（93% / 80% vs 78%）因来源而异。

### 仍待核实

- 各层级的**权威定义**尚无官方文档；现有说法多为第三方逆向或转述。
- Token 阈值与模型版本（Opus 4.6、Sonnet 4.6/4.5）随版本变化。
- `cache_edits` / `cache_reference` 是否为 Anthropic 公开 API，需查官方文档确认。
